## 5.1 環境は 3 層

| 環境 | 用途 |
| --- | --- |
| **ローカル Docker** | 日常開発の主軸 |
| **クラウド dev** | プレビューデプロイの接続先・スマホ実機確認 |
| **クラウド production** | 本番 |

Supabase はローカルで Docker 上にフルスタック（DB + 認証 + ストレージ + Edge Functions）を
立てられます。日常の開発はここで行います。

### ローカルを主軸にした理由

- **マイグレーションの試行錯誤が速い。** データベースを丸ごとリセットするのが一瞬で済む
- **クラウドの無料枠を温存できる。** 開発で通信量を使わず、本番に集中させられる
- **オフラインで開発できる**
- **CI と同じ構成**なので「ローカルで通る = CI で通る」が成り立つ
- 認証メールをローカルのメールサーバーで確認できる

クラウド dev が必要なのは、**プレビューデプロイがクラウドのデータベースを要求する**からです。
あとスマホの実機確認にプレビュー URL が便利、という実務的な理由もあります。

## 5.2 GitHub Actions

8 本の workflow があります。

| workflow | 役割 |
| --- | --- |
| 静的チェック | lint / 型チェック |
| E2E | Playwright によるブラウザテスト |
| DB テスト | pgTAP |
| マイグレーション適用（dev / prod） | スキーマ変更の反映 |
| Edge Functions デプロイ（dev / prod） | 関数の配信 |
| dev の自動復帰 | 後述 |

### E2E と DB テストを「全部の PR」では走らせない

これは意識的なトレードオフです。

```
feature ブランチ → topic ブランチ の PR    … CI では走らせない（ローカルで確認）
topic / feature → develop / main の PR    … 自動実行する
```

理由は**時間**です。E2E も pgTAP も、Supabase を起動してデータベースをリセットするところから
始まるので、それなりに時間がかかります。開発初期は E2E のカバレッジも薄く、
毎 PR で回す価値がコストに見合いませんでした。

代わりに、**develop と main へ入る手前では必ず通します**。
デグレを検出したいのはそこだからです。

さらに、**ドキュメントだけの PR ではスキップ**します。
ただし SQL や実装が混ざっている PR では通常どおり実行されます
（「変更ファイルが*すべて*除外パターンに合致する場合だけスキップ」という挙動を利用）。

> この判断は**サービスの成熟度で変わります**。E2E のカバレッジが厚くなったら、
> 毎 PR 実行に戻す前提で workflow にコメントを残してあります。

### 本番デプロイの事故を構造で防ぐ

Edge Functions の本番デプロイ workflow には、手動実行のトリガーを付けています。
無料枠が尽きたときなどに再デプロイしたいからです。

ところが手動実行は、**任意のブランチやタグを選べます**。
うっかり develop や作業ブランチを選ぶと、**未レビューのコードが本番に出ます**。

対策として、**main 以外は処理の最初で落とす**ようにしました。

```
checkout する前に ref を検証し、main でなければ失敗させる
```

「気をつける」ではなく「**構造的に不可能にする**」方が確実です。

あわせて、同時デプロイを防ぐ設定（concurrency）も入れています。
連続で push しても直列に処理されます。

### dev 環境の自動復帰

Supabase の無料プロジェクトは、一定期間アクセスが無いと**一時停止**します。
開発を再開するたびに手動で復帰させるのは面倒です。

そこで、**PR を作ったときに dev プロジェクトを自動で復帰させる** workflow を入れました。
プレビューデプロイが動き出す前に、接続先が起きている状態になります。

小さい自動化ですが、地味に効いています。

## 5.3 バッチ処理

ぴたスコアの再計算、タグの集計、ストレージの匿名化、退会予告の処理など、
定期実行が必要なものがいくつもあります。

**pg_cron**（PostgreSQL 内のスケジューラ）+ **Edge Functions** の組み合わせで回しています。

### 監視の経路は、監視対象と同じ層を通さない

ここが一番の学びでした。

バッチが失敗したことに気づく仕組みが必要です。最初はこう考えました。

```
DB のバッチ → アプリ（Vercel）のエンドポイント → Sentry へ通報
```

**動きませんでした。** Vercel のデプロイ保護機能が、
リクエストを**アプリに届く前に 401 で弾いた**のです。

もっと重要な問題に気づきました。

> **監視の通報経路が、監視対象と同じ層を通っていると、
> その層が落ちたときに通報も一緒に消える。**

Vercel が落ちていたら、「Vercel が落ちている」という通報も届きません。
これでは監視になりません。

現在はこうしています。

```
DB → Supabase Edge Functions → Sentry
（Vercel を一切経由しない）
```

### 「検知できているのに誰も知らない」を避ける

もう 1 つ、設計で気をつけた点があります。

通報には環境名（production / development）を付けます。
Sentry のアラートルールが環境で絞り込んでいるためです。

当初、環境変数が未設定のときは `development` に倒す実装でした。
これは**本番で設定が漏れたときに最悪の壊れ方**をします。

```
イベントは Sentry に届く
  → でも environment が development なので
  → production 向けのアラートルールに一致しない
  → 通知が飛ばない
  → しかも「通報済み」として記録されるので、抑制期間中ずっと誰にも知らされない
```

**「検知できているのに誰も知らない」は、無監視より悪い**です。
気付く機会があったと錯覚してしまうからです。

現在は**既定値を持たせず、設定が不正なら何もせずに終了**します。
通報できない状態では、「通報済み」の記録も進めません。

### 応答の収集をどこでやるか

DB から外部へ HTTP リクエストを出す仕組み（pg_net）は、
**レスポンスを一定時間で破棄**します。

この「応答を回収する処理」を Edge Functions 側に置くと、
デプロイ漏れや障害で関数が動かない間に**応答が消えて、成否が永久に分からなくなります**。

そのため、回収は **cron の SQL 側で完結**させています。
Edge Functions は「回収済みの結果を Sentry の形にして送る」だけの薄い役割です。

## 5.4 監視

| 対象 | 手段 |
| --- | --- |
| エラー | Sentry |
| パフォーマンス（実ユーザー） | Sentry（[3 章](./03-frontend.md)） |
| アクセス解析 | GTM + GA4（同意管理付き） |
| インフラのログ | Vercel / Supabase のログ |
| バッチの健全性 | 自作の健全性チェック（5.3） |

Sentry はエラー監視として入れましたが、**Web Vitals の収集も兼ねている**ので、
計測用のパッケージを追加せずに済んでいます。

エラーについては、「このエラーが出たらどう対処するか」を
**カタログとしてドキュメント化**しています。
個人開発でも、3 ヶ月後の自分は他人です。

## 5.5 良かった点・つらい点

### 良かった点

- **ローカル主軸は完全に正解だった。** マイグレーションを 176 本書けたのは、
  リセットが一瞬で終わるからです。クラウドだけだったら試行錯誤の回数が 1 桁減っていました
- **CI の実行範囲を絞ったのは、開発速度に直結した。** 全 PR で E2E を回していたら、
  待ち時間で開発リズムが崩れていたと思います
- **通報経路を分離したのは、事故を 1 つ未然に防いだ。**
  Vercel 経由のままだったら、障害時に何も気づけませんでした

### つらい点

- **3 層あると、どこに何を反映したか分からなくなる時がある。**
  「dev には入っているが prod にはまだ」という状態の管理は、頭で覚えるには多すぎます
- **Edge Functions のデバッグがしづらい。** ローカルでも動かせますが、
  本番特有の問題（シークレットの設定漏れなど）はデプロイしないと分かりません
- **CI の実行条件が複雑になってきた。** ブランチとパスの組み合わせで分岐しているので、
  「なぜこの PR で CI が走らないのか」を追うのに時間がかかることがあります

## 5.6 まとめ

- 環境は **ローカル Docker 主軸**。リセットの速さが試行錯誤の回数を決める
- CI は**全部走らせない**。develop / main の手前でだけ通す
- 本番デプロイの事故は「気をつける」ではなく**構造で防ぐ**
- **監視の通報経路を、監視対象と同じ層に通さない**
- 「検知できているのに誰も知らない」は**無監視より悪い**
