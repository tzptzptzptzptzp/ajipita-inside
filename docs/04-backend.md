## 4.1 データアクセスを 1 箇所に集約する

### 最初は直アクセスだった

当初は、画面から直接データベースを叩く構成でした。
Supabase は RLS があるので、クライアントから直接アクセスしても行レベルの権限は守られます。
実装も速い。

これを **BFF（Backend For Frontend）に一本化**しました。

### なぜ変えたか

理由は 3 つありました。

1. **将来ネイティブアプリを出したい。** Web と同じデータ操作を共有したいが、
   直アクセス方式だと「どういう操作が許されるか」の契約が暗黙になる
2. **バックエンドを別言語に切り出す可能性。** 独立した HTTP 契約があれば、移行が契約の再実装で済む
3. **横断的な処理を 1 箇所にまとめたい。** 入力検証・レート制限・外部 API キーの隠蔽。
   直アクセスだと各画面に散ります

### 素朴に全 HTTP 化すると失敗する

ただし、「全部 API 経由にする」と決めると罠があります。
**Server Component から自分自身の API を fetch する**という構成です。

これはアンチパターンです。同じサーバー上で動いているのに、
わざわざ HTTP のラウンドトリップを挟むことになります。

そこで、**ロジックの置き場所と、到達方法を分けました**。

![データアクセス境界](./diagrams/data-access.svg)

- **データモジュール**: DB アクセスとビジネスロジックの実体。ここが唯一の真実
- **API ルートハンドラ**: 認証・入力検証・エラー整形だけを行う**薄いアダプタ**。ロジックを持たない
- **Server Component**: モジュールを**直接呼ぶ**（自己 HTTP しない）
- **Client Component**: API を叩く

こうすると、**ロジックは 1 箇所にありながら、到達方法は用途ごとに選べます**。

サーバー専用モジュールには `import 'server-only'` を付けて、
クライアント側に混入したらビルド時に落ちるようにしています。

## 4.2 RLS と GRANT は別のレイヤーである

ここが**一番痛い失敗**をした箇所です。

### 起きたこと

プレビュー環境で、診断が未完了のユーザーが特定の画面で **404 になり、そこから脱出できなくなる**
という事故が起きました。

調べると、データベースがこう言っていました。

```
permission denied for table tags
hint: GRANT SELECT ON public.tags TO anon;
```

RLS ポリシーは正しく設定されていました。「全員が読める」というポリシーです。
**なのに読めない。**

### 原因

PostgreSQL では、**テーブル権限（GRANT）と行の可視性（RLS）は別のレイヤー**です。

```
読めるかどうか = GRANT がある  AND  RLS ポリシーを通る
```

RLS ばかり気にしていて、**GRANT を暗黙の前提にしていました**。

Supabase はテーブルを作ると自動で GRANT を付けてくれます。
ローカルや通常のマイグレーション適用では、これが効きます。
ところが**別経路で適用した環境では、この自動付与が効かず、GRANT が一切付いていませんでした**。

書き込み権限は各マイグレーションで明示的に書いていたので無事でした。
**SELECT だけが暗黙依存で抜け落ちていた**のです。

### 直し方

暗黙の前提を、**明示的な宣言に変えました**。

- ベースラインの GRANT をマイグレーションとして書く
- 今後作られるテーブルにも自動で付くよう、デフォルト権限も宣言する
- このマイグレーションは冪等なので、**適用すれば壊れた環境も復旧する**

さらに、アプリ側も直しました。データ取得に失敗したとき `404` を返していたのが問題で、
**リダイレクトのループと組み合わさって脱出不能**になっていました。
エラー画面に倒してリトライできるようにしています。

> **教訓**: 「フレームワークが自動でやってくれる」に依存すると、
> **その自動が効かない経路で静かに壊れます**。
> スキーマは自己完結させる。暗黙を明示に変える。

### 権限を「配らない」という判断

逆に、**あえて権限を外している**テーブルもあります。

従量課金 API の呼び出し上限を記録する台帳です。
上限の判定は「台帳に何行あるか」で行うため、
**行を消せる権限は、上限をリセットできる権限と同義**になります。

そのため、この台帳だけはベースラインの権限付与から除外し、
**管理者権限のロールからも剥奪**しました。
上限を判定する関数自体が特別な権限で動くので、呼び出し側にテーブル権限は要りません。

これは机上の心配ではなく、**実際に再現を確認**しています。
管理者権限で台帳の行を削除すると、上限がリセットされて再び外部 API を呼べてしまう。
剥奪後はその経路が閉じます。

詳しくは[6 章](./06-cost.md)で扱います。

## 4.3 DB のロジックをテストで固定する

あじぴたはビジネスロジックの一部を DB の関数として持っています。
マッチングの集計、ゲーミフィケーションの判定、上限の消費など。

これらは **pgTAP**（PostgreSQL 用のテストフレームワーク）でテストしています。
現在 **79 ファイル**。

### 「持たないこと」をテストする

面白い使い方ができたので紹介します。

外部 API の呼び出し回数を記録するテーブルがあります。
これはコストの試算に使うもので、**個人を特定する情報を持たせたくない**。

そこで、**その列が存在しないことをテストで固定**しました。

```
このテーブルに user_id / IP / 検索キーワードの列が「無い」ことを検証する
```

普通、テストは「あるべきものがあるか」を確かめます。
でもプライバシーに関わる設計では、「**無いべきものが無いか**」の方が重要です。

将来「この列があれば便利だな」と思って足したとき、**テストが落ちて理由を思い出せます**。
コメントに書いておくだけでは、こうはなりません。

## 4.4 退会処理をどう設計したか

地味ですが、設計判断が最も多く必要だった領域です。

### 問題

退会したユーザーのデータをどう扱うか。

- **全部消す** → その人の口コミが消え、料理ページが空になる。他のユーザーの推薦精度も落ちる
- **全部残す** → 個人情報が残り続ける。退会の意味がない

### 採った方針: 評価の種類ごとに扱いを変える

| データ | 扱い | 理由 |
| --- | --- | --- |
| 個人情報 | **削除** | 当然 |
| 「美味しかった」の評価 | **匿名化して残す** | 他ユーザーの推薦精度と、料理ページの表示を保つ |
| **「合わなかった」の評価** | **完全削除** | **サイレントネガティブの漏洩リスクを根絶する** |
| 店舗のお気に入り | 削除 | 個人の嗜好情報 |
| 味覚プロファイル | 削除 | 退会者の分は不要 |
| 料理の写真 | 匿名化して残す | 料理ページの視覚情報を維持 |

### なぜ negative だけ完全削除なのか

匿名化は「誰のものか分からなくする」処理です。
ですが**匿名化されたデータでも、条件が揃えば推定できる**ことがあります。

サイレントネガティブは**漏れた瞬間にサービスの信頼が終わる**データです。
「推定される可能性が残る」こと自体が許容できません。

一方、positive の評価は**元々公開されている**情報です。
匿名化して残しても新たなリスクは生まれません。

**リスクの非対称性に応じて、扱いを変えた**形です。

### 匿名化の方法

「退会ユーザー」を表す固定のアカウントを 1 つ用意し、
退会者の評価の紐付けをそこへ差し替えます。

表示上は「退会したユーザー」として出ます。

### トランザクションに入れられないものをどう扱うか

DB 側の処理は 1 つのトランザクションにまとめています。
ところが、**写真（ストレージ）だけは同じトランザクションに入れられません**。
ファイル操作の API を叩く必要があり、SQL で完結しないためです。

つまり「DB は消えたが写真が残る」という中途半端な状態が起こりえます。

そこで、こうしました。

> **退会と同じトランザクションで、再試行キューに対象を積む。**

リクエストが途中で落ちても、**再実行の起点が必ず DB に残ります**。
定期実行の処理が、キューを見て冪等に再試行します（試行回数に上限あり）。

写真の処理が失敗しても退会自体は成功扱いにしますが、**握り潰しません**。
失敗はキューに残り続け、後から必ず回収されます。

**トランザクションに入れられないものは、トランザクション内に「やり残しの記録」を残す。**
整合性を保証できない境界がどこかを見極めて、そこに再試行の起点を置く形です。

ハンドル名（`@xxx`）は即座に解放して、新規ユーザーが使えるようにしています。

## 4.5 マイグレーション 176 本の運用

### 基本方針

- **マイグレーションは web リポジトリだけが持つ**（[1 章](./01-architecture.md)）
- 1 つの変更 = 1 ファイル。まとめない
- ファイル名に日時とスラッグを入れて、時系列で並ぶようにする

### やってよかったこと

**ロールバック用のマイグレーションを書かない。** 前に進むだけにしています。

個人開発だと「巻き戻したい」場面はほぼ無く、
あったとしても「打ち消すマイグレーションを新しく書く」方が状態が明確です。
down マイグレーションを書くコストと、それが正しく動くか検証するコストが見合いませんでした。

**冪等に書く。** 同じマイグレーションを 2 回流しても壊れないようにしておくと、
環境の状態がずれたときに「とりあえず全部流す」で復旧できます。
4.2 節の事故はこれで救われました。

## 4.6 良かった点・つらい点

### 良かった点

- **BFF への一本化は、思ったより早く効果が出た。** 外部 API キーの扱い、レート制限、
  入力検証がすべて 1 箇所に集まったので、「ここを見ればいい」状態になりました
- **pgTAP を入れたのは正解。** DB の関数はアプリのテストでは守れません。
  マイグレーションを重ねるほど、この安心感が効いてきます
- **退会処理を早めに設計した。** 後回しにすると、データが増えてから考えることになります

### つらい点

- **GRANT の事故は防げたはずだった。** 「Supabase が自動でやってくれる」で思考を止めたのが原因です。
  同じ理由の事故は他にもありそうで、暗黙依存を洗い出す作業が残っています
- **BFF はエンドポイントを書く手間がかかる。** 直アクセスなら 1 行で済むものに、
  ルートハンドラと検証を書くことになります。将来の移植性のための前払いです
- **マイグレーション 176 本は、新しい環境の構築が遅い。** 全部流すのに時間がかかります。
  どこかで 1 本にまとめる（スカッシュする）必要が出てきそうです

---

## 4.7 まとめ

- データアクセスは BFF に一本化。ただし**ロジックの置き場所と到達方法を分ける**
- **RLS と GRANT は別レイヤー。** 両方揃わないと読めない
- フレームワークの自動処理に依存すると、**効かない経路で静かに壊れる**
- 上限の台帳は、**行を消せる権限 = 上限をリセットできる権限**なので誰にも配らない
- プライバシー設計では「**無いべきものが無いこと**」をテストで固定する
- 退会処理は**リスクの非対称性**に応じて扱いを変える
