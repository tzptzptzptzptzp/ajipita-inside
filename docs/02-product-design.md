# 2. プロダクト設計

← [トップに戻る](../README.md) | [← 1. 全体構成](./01-architecture.md)

---

この章は、あじぴたが**何を解こうとしているサービスなのか**の記録です。
技術選定の話は出てきませんが、ここを飛ばすと後の章の判断が読めません。

先に結論を書くと、**「ネガティブな評価を表に出さない」という 1 つの方針**が、
UI・データモデル・RLS・そしてデータベースの選定まで、一直線に決めています。

---

## 2.1 なぜ作ったか — ネガティブのない場所を作りたかった

あじぴたの出発点は、技術でもビジネスでもなく、**既存の口コミサービスへの違和感**でした。

### 低評価が、店を閉店に追い込むことがある

飲食店の口コミには、星 1 つのレビューが並ぶことがあります。
その 1 件が「たまたまその日が悪かった」だけでも、平均点は下がり、
検索結果での表示順は落ち、客足は遠のきます。

**評価を書いた側にコストはありません。でも店側は、それで潰れることがある。**

個人が営む小さな店ほど、この影響を強く受けます。
大手チェーンなら何百件のレビューに埋もれる 1 件が、
口コミ 10 件の店では平均点を大きく動かしてしまう。

### そもそも、自分に合う一皿を探すのにネガティブは要らない

もう一つ思ったのは、**自分が食べたいものを探すという目的に、
他人の低評価は本当に必要なのか**ということでした。

「この店は 2.8 点」と言われても、それは自分にとっての 2.8 ではありません。
知りたいのは「**自分と味覚が近い人が、何を美味しいと言ったか**」だけです。

### 「店の評価が低かろうが、私はこれが好き」が守られてほしい

評価の低い店に、自分にとっての最高の一皿があることは普通にあります。
点数が低いという理由でその店が候補から外れ、あるいは店自体が無くなってしまうのは、
**食べる側にとっても損失**です。

だから、あじぴたはこう決めました。

> **ネガティブな評価を、表に出さない。**
> 公開するのは「美味しかった」だけ。

これは機能の取捨選択ではなく、**このサービスが存在する理由**です。
以降の設計判断は、すべてこの一点から降りてきています。

---

## 2.2 解こうとしている問題

思想の話に加えて、実用上の課題もあります。
既存の口コミサービスは**店単位・大衆平均**で評価を出しますが、この構造には 2 つの限界があります。

**1. 平均は誰の好みでもない**

4.2 点の店が自分に合うかは、その 4.2 を付けた人たちと自分の味覚が近いかによります。
でも普通、それは分かりません。

**2. 店単位だと料理の情報が埋もれる**

「店全体は普通だが、この一品だけは絶品」「看板メニューより裏メニューが当たり」——
こうした情報は店単位の評価では表現できません。

---

## 2.3 3 つの設計判断

### 判断 1: 評価の単位を「店」ではなく「料理」にする

|            | 既存サービス | あじぴた         |
| ---------- | ------------ | ---------------- |
| 評価の単位 | 店           | **料理（dish）** |

これがサービスの出発点です。「あの店の油そばが良かった」を、店ではなく料理に紐づけて記録します。

副次的な効果として、**マッチングの精度が上がります**。
店単位だと「同じ店に行った人」しか比較できませんが、料理単位なら
「同じ料理を食べた人」で比較できる。**重複が発生しやすくなる**ので、
少ないデータでも類似度が計算できます。

### 判断 2: 公開するのは「美味しかった」だけにする

評価は 5 段階ではなく、「美味しかった」の一択。
さらに「なぜ美味しかったか」を**理由タグ**（`うま味・出汁感`・`サクサク`・`とろける` など）で付けます。

理由は 2 つあります。

- **投稿ハードルを下げる。** 星をいくつ付けるか悩ませない
- **味覚プロファイルが自動で貯まる。** タグの傾向が、そのユーザーの好みの輪郭になる

タグは**ポジティブ専用**です。「合わなかった」理由のタグは作りませんでした。
ネガティブな理由を言語化させると、サービス全体のトーンが変わってしまうためです。

そしてタグは**味覚に関するものだけ**に絞っています。
「コスパ」「量」「見た目」のような**店や取引の属性**、
そして誰でも肯定するような無差別語は、意図的に入れていません。

味覚プロファイルを作るのが目的なので、**味覚以外の語はノイズになる**からです。
「コスパが良い」が一致しても、味の好みが近いことにはなりません。

### 判断 3: 「合わなかった」を**非公開で**記録する ← 設計の根幹

ここがあじぴたの中核です。

**「合わなかった」は記録するが、本人以外には絶対に見せない。**

なぜ記録するのか。**一致だけでは味覚の近さを測れないから**です。

```
A さんと B さんが、同じ 5 品に「美味しかった」を付けている
  → 一見、味覚が近そうに見える

でも実は、別の 10 品で正反対の評価をしていたら？
  → 2 人は全く似ていない
```

公開されている「美味しかった」だけを見ていると、この**裏側のズレが見えません**。
「合わなかった」を内部で持つことで、一致と不一致の両方を使って類似度を出せます。
見かけ上似ているのに実は味覚が違う人を、正しく除外できる。

### 公開しない理由は、2.1 に書いたとおり

**店を傷つけないため**です。低評価が可視化されないので、
1 件のレビューが店の評価を下げることも、それが閉店につながることもありません。

副次的に、**ユーザーも正直になれます**。
公開されると人は忖度します。「この店に悪いかな」と思えば、
合わなかったものも「合わなかった」と付けにくい。
**誰にも見られないと分かっているから、正直に付けられる**。

そしてその正直な記録が、そのままマッチングの精度になります。

> **店を守るための仕様が、結果として推薦の精度も上げている。**
> ここが自分でも気に入っている点です。倫理と性能が同じ方向を向きました。

この「記録するが見せない」という仕様を、あじぴたでは**サイレントネガティブ**と呼んでいます。

---

## 2.4 サイレントネガティブが技術選定を決めた

ここからが、この章を最初に置いた理由です。

サイレントネガティブは、**外に漏れた瞬間にサービスが終わる**種類のデータです。
「あの人は私の店の料理に合わなかったを付けている」が見えてしまったら、
ユーザーは二度と正直に評価しません。信頼の前提が崩れます。

つまり要件はこうなります。

> **非公開の保証が、サービスの信頼性そのもの。アプリのバグ 1 つで漏れてはいけない。**

アプリケーション層のコードだけで守ると、
「このクエリに WHERE 句を付け忘れた」で全件漏洩しうる状態になります。
**データベース自身が、行レベルで見せる・見せないを強制する必要がある。**

これは PostgreSQL の **RLS（Row Level Security）** で実現できます。
そして、この要件が BaaS の選定を決めました。

### 選定の経緯

データベース基盤を選ぶとき、コスト効率の良い候補がいくつかありました。

| 候補                   | DB         | RLS                  | 判定    |
| ---------------------- | ---------- | -------------------- | ------- |
| **Supabase**           | PostgreSQL | **ネイティブ対応**   | ✅ 採用 |
| Cloudflare D1 + 別認証 | SQLite     | **無し**（自前実装） | ❌      |
| Turso + 別認証         | SQLite     | **無し**（自前実装） | ❌      |

SQLite ベースのサービスは、**RLS という機能自体を持ちません**。
権限制御をアプリケーション層で書くことになり、それは上に書いた
「バグ 1 つで全件漏洩」の状態そのものです。

料理名のあいまい検索に PostgreSQL の拡張機能（`pg_trgm`）を使いたかったこと、
認証を別サービスで契約すると**トータルコストがむしろ高くなる**ことも重なり、
Supabase に決まりました。

**「店ではなく料理を評価する」→「合わなかったを非公開で持つ」→「RLS が必須」→「PostgreSQL 系」**

プロダクトの仕様が、インフラの選定まで一直線に降りてきた形です。
技術から入っていたら、おそらく別の結論になっていました。

## 2.5 マッチングの考え方

味覚の近さ（あじぴたでは **ぴたスコア** と呼んでいます）の算出方法は、
サービスのコアにあたるため非公開とします。

ここでは 1 点だけ、設計の方針として書けることを残しておきます。

### 精度より「説明できること」を優先した

推薦システムの定石として、評価データから潜在的な特徴ベクトルを学習する手法があります。
大手の推薦エンジンで実績があり、スケーラビリティも高い。

あじぴたでは採用しませんでした。理由は**説明できないから**です。

あじぴたの画面は「**ぴたスコア ◯% の〇〇さんが美味しかったと言っている**」という形で
推薦を出します。この UI が成立するには、「なぜこの人と味覚が近いのか」を
**データとして説明できる**必要があります。

潜在ベクトルを使う手法では、「学習された特徴量が近いから」としか言えません。
ユーザーに見せられないし、推薦がおかしいときのデバッグもしづらい。

推薦の理論的な精度そのものより、**推薦の理由が言えること**を優先した判断です。
計算量の問題は、夜間バッチと事前計算で解いています（[5 章](./05-infrastructure.md)）。

---

## 2.6 意図的にやらないこと

差別化を濁すため、以下は実装していません。

| やらないこと                              | 理由                                                                                   |
| ----------------------------------------- | -------------------------------------------------------------------------------------- |
| 店の総合評価スコア（「この店は 4.2 点」） | 大衆平均を主役にした時点で、既存サービスと同じになる                                   |
| フォロー機能                              | ソーシャル性はコア体験を弱める。見たいのは「味覚が近い人」であって「知り合い」ではない |
| ネガティブ評価の公開                      | **サービスの存在理由そのものが崩れる**（2.1）                                          |

**何をやらないかを決めておくのは、何をやるかと同じくらい重要**でした。
機能追加の判断に迷ったとき、ここに立ち返れば答えが出ます。

特に最後の 1 行は、**どれだけ要望が来ても変えない**と決めている項目です。
「低評価も見たい」という声は当然あり得ますが、それを入れた瞬間、
あじぴたは既存の口コミサービスと同じものになります。

---

## 2.7 まとめ

- 出発点は**「ネガティブのない場所を作りたい」という思想**。低評価が店を潰すことへの違和感
- 料理単位の評価にしたのは、**店単位では埋もれる情報を扱う**ため。副次効果でマッチング精度も上がる
- 「合わなかった」を**非公開で記録する**のがサービスの根幹。
  店を守るための仕様が、結果として推薦精度も上げている
- この 1 つの仕様が、**RLS 必須 → PostgreSQL 系 → Supabase** という技術選定まで決めた
- マッチングは精度より**説明可能性**を優先した
