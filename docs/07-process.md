# 7. 開発プロセス

← [トップに戻る](../README.md) | [← 6. コスト](./06-cost.md)

---

5 ヶ月で 4,100 コミット（アプリ本体だけで 3,400）。1 人でこの量を回すために何をしたかの記録です。

---

## 7.1 個人開発でも develop を切る

ブランチは **main + develop の 2 階層**です。

```
main      ← 本番。ここに入ったものが公開される
develop   ← 統合先。ここで検証してから main へ
feature/* ← 作業ブランチ。Issue 1 つに対して 1 本
topic/*   ← 複数 Issue を束ねるときだけ使う
```

1 人なのに develop を切る意味はあるのか。ありました。

- **本番に出す前の緩衝地帯**が要る。develop で動かしてから main へ入れる
- プレビュー環境の接続先が develop なので、**実機確認の場所**になる
- 「今どこまで本番に出ているか」が main を見れば分かる

topic ブランチは、**複数の Issue をまとめて 1 つの PR にしたいとき**だけ使います。
常用はしません。階層が深くなると、どこに何があるか分からなくなるからです。

## 7.2 マージは merge commit だけ

GitHub のマージ方式は 3 種類ありますが、**merge commit のみ**を有効にしています。
Squash と Rebase は設定で無効化しました。

### なぜ Squash を使わないか

Squash は「1 PR = 1 コミット」に圧縮する方式で、履歴がきれいになります。
**それが嫌でした。**

あじぴたはコミットを細かく切る運用をしています。
絵文字 + 短文で「何をしたか」が分かる粒度です。

```
✅ 複製カードが読み上げ・タブ順に重複しないことを e2e で固定する
🐛 カーソル未読時は走査できても書き込まない
♿ マーキーの複製カードを支援技術とタブ順から外す
```

Squash すると、この粒度が**全部消えます**。
後から「なぜこの実装になっているのか」を追うとき、
細かいコミットが残っている方が圧倒的に読めます。

merge commit なら「この時点でこの機能が入った」も明確で、
PR 単位でのリバートも簡単です。

## 7.3 判断を ADR として残す

**ADR（Architecture Decision Record）** を 36 本書いています。
「なぜその技術・設計を選んだか」を 1 ファイルにまとめたものです。

構成はこの形に統一しています。

```
## ステータス       承認済み（日付）
## 背景            何が問題で、なぜ決める必要があったか
## 検討した選択肢    案の比較表
## 決定            結論
## 理由            なぜそれを選んだか
## 影響範囲         関連する仕様・コード
## 関連リンク       関連する ADR・資料
## 履歴            いつ書いたか、いつ更新したか
```

### なぜ個人開発で書くのか

チーム開発なら「合意の記録」として必要です。でも 1 人なら要らないのでは、と思うかもしれません。

**3 ヶ月後の自分は他人**でした。

「なぜこうなっているんだっけ」を思い出すコストが、書くコストを上回ります。
特に、**採用しなかった案を書いておく**のが効きます。
同じ検討を 2 回しなくて済むからです。

### 前提が崩れたら更新する

ADR は書いて終わりではありません。**前提が失効することがあります**。

実際に起きた例:

```
ADR-0027（当時）: 「外部 API は月 $200 の無料クレジット内で運用する」
     ↓
Google が 2025-03-01 に $200 クレジットを廃止
     ↓
前提そのものが成立しなくなった
     ↓
ADR-0036 で是正し、旧 ADR に「この前提は失効した」と追記
```

**古い ADR を消さずに、失効を記録する**のが重要だと思っています。
消すと「なぜ方針が変わったか」が追えなくなります。

詳しくは[6 章](./06-cost.md)に書きました。

## 7.4 AI との協業

開発は Claude Code を使っています。この量の多くはこの体制で回しました。

### 文脈をどう渡すか

AI に毎回ゼロから説明するのは非効率です。
**文脈をファイルとして置いておく**ことで解決しました。

| 置き場所 | 内容 |
| --- | --- |
| `AGENTS.md` | このリポジトリのルール。最初に読ませる |
| `docs/development/rules.md` | 命名・配置・実装の規約 |
| `docs/decisions/` | 過去の判断（ADR） |
| `docs/requirements/` | 仕様 |

**ADR が予想外に効きました。**

もともと「未来の自分のため」に書いていたのですが、
**AI にとっても最良の入力**でした。「なぜこうなっているか」が書いてあるので、
既存の設計を壊す提案が減ります。

### 繰り返す作業をスキル化する

同じ手順を毎回説明するのが面倒だったので、**カスタムスキル**として登録しました。
現在 13 個あります。

| スキル | 内容 |
| --- | --- |
| `work-on-issue` | Issue を 1 つ選んで実装する |
| `create-pr` | 受け入れ条件を照合して PR を作る |
| `handle-review` | レビュー指摘に対応してコミット・返信する |
| `refine-issue` | 雑に起票した Issue を着手可能な粒度まで詰める |
| `commit-changes` | 差分を適切な粒度でコミットする |
| `resolve-conflict` | コンフリクトを解消する |
| ほか 7 個 | 環境構築・ドキュメント同期・リリース監査など |

**雑に起票して後で詰める**というフローが特に効いています。
思いついた瞬間は 1 行だけ書いておき、着手前に `refine-issue` で
背景・受け入れ条件まで具体化する。アイデアを取りこぼさなくなりました。

### レビューを挟む

PR には Copilot のレビューを入れています。
1 人だと**レビューが存在しない**のが構造的な弱点なので、そこを埋める目的です。

実際、このドキュメントに書いた設計判断のいくつかは、
レビュー指摘がきっかけで見直したものです。

- 上限の台帳テーブルの権限を、管理者ロールからも剥奪した（[4 章](./04-backend.md)）
- Places の発火条件を純関数に切り出してテストで固定した（[6 章](./06-cost.md)）
- 計測でリダイレクトされた試行を中央値から除外した（[3 章](./03-frontend.md)）

### 運用作業もツールで潰す

サービスを運用していると、手作業で繰り返すタスクが出てきます。
そういうものは**その都度ツールを作って潰す**方針です。

Chrome 拡張を自作していて、運用の手間をかなり減らせました。

## 7.5 Issue の管理

### 子 Issue は本文のチェックリストにしない

大きな作業を分割するとき、2 つの方法があります。

| 方法 | 問題 |
| --- | --- |
| 本文にチェックリストを書く | 進捗が本文の編集でしか分からない。担当・状態を持てない |
| **GitHub の Sub-issues 機能を使う** | それぞれが独立した Issue として状態を持つ |

後者を採用しました。子 Issue それぞれに PR が紐づき、
親から進捗が一覧できます。

### ラベルで分類する

ラベルの運用ルールをドキュメント化して、4 リポジトリで揃えています。
種類（feature / bug / chore …）と状態（draft など）を分けて付ける方式です。

## 7.6 良かった点・つらい点

### 良かった点

- **ADR を書く習慣は、最大の投資だった。** 判断のたびに 15 分かけて書くだけで、
  後から何度も助かりました。AI への入力としても効きます
- **スキル化は複利で効く。** 最初に 30 分かけて手順を書くと、以降ずっと省略できます
- **コミットを細かく切る運用は、履歴が資産になる。**
  「なぜこの実装か」を git log から追えます
- **雑に起票して後で詰めるフロー。** アイデアを取りこぼさずに済みます

### つらい点

- **ドキュメントの量が、1 人で把握できる限界を超えた。**
  ADR 36 本 + 要件定義 10 章 + 開発ドキュメント 15 本。
  書いた本人が全体を覚えていられません。**このドキュメント自体が、その対策でもあります**
- **ADR の更新を忘れる。** 前提が変わっても、気づくのは何か月も後です。
  「失効したら追記する」運用は、失効に気づく仕組みとセットでないと機能しません
- **スキルが増えすぎて、どれを使うべきか迷う時がある。** 13 個は 1 人には多いかもしれません
- **AI に任せた部分のコードを、自分が完全には把握していない。**
  レビューはしていますが、「全部を頭に入れている」状態ではありません。
  規模が大きくなるほどこれは避けられず、ドキュメントとテストで補っています

---

## 7.7 まとめ

- 1 人でも **develop を切る**。本番の手前に緩衝地帯を作る
- **Squash しない**。細かいコミット履歴は後から読める資産になる
- **ADR は未来の自分のため**に書く。そして AI への最良の入力にもなる
- **前提が崩れた ADR は消さず、失効を記録する**
- 繰り返す作業は**スキル化**して複利で回収する
- 1 人開発の弱点は**レビューが無いこと**。AI レビューで埋める

---

## おわりに

このドキュメントは、**自分が全体像を把握するため**に書き始めました。
5 ヶ月で 4 リポジトリ・4,100 コミットまで来ると、
作った本人でも「あそこはどうなっていたか」が出てこなくなります。

書いてみて分かったのは、**判断の理由を残しておくと、後から構造が見える**ということでした。
個々の実装は忘れても、「なぜそうしたか」が残っていれば再構成できます。
