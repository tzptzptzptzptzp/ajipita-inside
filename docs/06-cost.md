# 6. コスト

← [トップに戻る](../README.md) | [← 5. インフラ・CI/CD](./05-infrastructure.md)

---

個人開発で一番シビアなのがここです。

会社なら「今期は赤字でも投資」と言えますが、個人開発では
**払えない金額になった時点でサービスが終わります**。
しかも請求は自分の財布から出るので、上限は生活費に直結しています。

だから、サービスが伸びるほどコストが上がる構造は
**成功した瞬間に破綻する**ことを意味します。
ユーザーが増えて嬉しいはずの状況が、そのまま終わりに繋がる。

この章に書いた設計は、ほぼすべて**その恐怖が動機**です。

この章は 2 部構成です。

- **6.1〜6.2**: 固定費の話（何にいくらかかっているか）
- **6.3 以降**: 従量課金の話（**伸びると破綻する構造をどう潰したか**）

---

## 6.1 コスト構造の全体像

| サービス | 役割 | 課金の性質 |
| --- | --- | --- |
| Vercel | フロントのホスティング | 固定（プラン） |
| Supabase | DB / 認証 / ストレージ | 固定（プラン） |
| Sentry | エラー・パフォーマンス監視 | 固定（無料枠） |
| Resend | メール送信 | 固定（無料枠） |
| **Google Maps Platform** | 地図・店舗検索 | **従量課金** ← 危険 |
| HotPepper API | 店舗情報 | 無料 |
| ドメイン | — | 固定（年額） |

**固定費は予測できます。従量課金は予測できません。**
だから設計の重心は従量課金側に置きました。

## 6.2 運用コストの実態

有料プランへ移行した後の固定費はこうなります。

| サービス | 用途 | プラン | 費用 |
| --- | --- | --- | --- |
| Vercel | アプリ本体 | Pro | **$20 / 月** |
| Supabase | DB / 認証 / ストレージ | Pro | **$25 / 月** |
| **Netlify** | 運営コンソール・LP | **無料枠** | **$0** |
| Sentry | 監視 | 無料枠 | $0 |
| Resend | メール送信 | 無料枠 | $0 |
| HotPepper API | 店舗情報 | 無料 | $0 |
| ドメイン | — | — | 年間数千円 |
| **合計** | | | **約 $45 / 月 + ドメイン代** |

**月 7,000 円程度**です。個人で継続できる水準に収まっています。

### ホスティングを分けてコストを抑えた

Vercel の有料プランは**アカウント単位**の契約です。
3 つのフロントエンドをすべて Vercel に載せても、料金は同じ $20。

ただし**ビルド時間や帯域はアカウント全体で共有**されます。
管理画面や LP が、ユーザーの触るアプリ本体のリソースを削る構図になる。

そこで、**商用利用可能な無料枠がある Netlify** に
アプリ本体以外を逃がしました（[1 章](./01-architecture.md)）。
追加コストはゼロで、Vercel のリソースは本体に集中します。

### 無料枠でどこまで戦えたか

リリースして運用に入るまで、**固定費はドメイン代だけ**でした。
開発期間中の 5 ヶ月、Vercel も Supabase も無料枠で足りています。

これは[5 章](./05-infrastructure.md)に書いた
**ローカル Docker 主軸の開発**が効いています。開発の主戦場をローカルに置いたので、
クラウド側の通信量をほとんど消費しませんでした。

### 移行の理由は「機能」ではなく「制限」

有料プランに移る理由は、**新しい機能が欲しいから**ではありませんでした。

Supabase の無料プランには、**一定期間アクセスが無いとプロジェクトが一時停止する**制限があります。
開発中は[自動で復帰させる仕組み](./05-infrastructure.md)で回避できますが、
**実際にユーザーがいる状態では許容できません**。

Vercel も同様で、無料プランは商用利用の扱いが制限されます。

つまり、**運用フェーズに入った時点で移行は必須**でした。
逆に言えば、それまでは無料枠で十分だったということです。

### Sentry と Resend は無料枠のまま

監視とメール送信は、現在も無料枠に収まっています。
この規模なら当面は足りる見込みです。

## 6.3 従量課金 API は「安く使う」ではなく「呼ばない」

ここからが本題です。

### 前提が崩れた

店舗情報の取得に Google Places API を使っています。
この API を採用したときの ADR には、こう書いてありました。

> 無料クレジット（月 $200）の範囲内で運用する

**この前提が失効しました。**

Google は 2025-03-01 に月 $200 の無料クレジットを廃止し、
**SKU ごとの無料コール数**（機能の階層ごとに月 5,000 件など）へ移行しました。

「クレジット内に収める」という考え方自体が成立しなくなったのです。

### さらに、課金階層の認識も間違っていた

当初の ADR には「安い階層のフィールドに限定してコストを抑える」と書いてありました。
**これも誤りでした。**

Google Places の課金は、**リクエストで要求したフィールドの中で最も高い階層**が適用されます。
そして、**店名（`displayName`）を含めた時点で上位階層**になります。

店名を取得しない店舗検索はあり得ません。
つまり、**上位階層の課金は避けられない**というのが正しい理解でした。

| 用途 | 単価（無料枠超過後） |
| --- | --- |
| 店舗検索（Text Search） | **$32 / 1,000 件** |
| 店舗詳細の取得（Place Details） | $17 / 1,000 件 |
| エリア名の解決（Geocoding） | $5 / 1,000 件 |

**単価が 6 倍違う**ので、後述の上限も経路ごとに変えています。

### 試算してみたら破綻していた

「ユーザー 1 人あたり月 10 回検索する」と仮定して試算しました。

| MAU | 月間リクエスト | 月額 |
| --- | --- | --- |
| 500 | 5,000 | **$0**（無料枠内） |
| 1,000 | 10,000 | **$160** |
| 2,000 | 20,000 | **$480** |
| 5,000 | 50,000 | **$1,440** |

**MAU 5,000 で月 $1,440。**

固定費が月 $45 であることを思い出してください。
**外部 API だけで固定費の 32 倍**です。個人開発で払える額ではありません。

**払えません、となったら終わり**です。機能を削るとかではなく、サービスが止まる。

**結論: 単価を下げる交渉はできない。呼ぶ回数を減らすしかない。**

## 6.4 8 層の防壁

「呼ばない」を実現するために、防壁を多層で入れました。

![店舗検索のコスト防壁](./diagrams/cost-barriers.svg)

### ① 外部 API を使わない経路を用意する

「あじぴた登録店のみ」という検索モードがあります。
これは自前のデータベースだけを引くので、**外部 API を一切呼びません**。

**この経路の利用比率が上がるほど、コストが下がります**。
だから後述の計測でも、この経路を同じ表で数えています。

### ② 発火条件を絞る

Places は**常に呼ぶわけではありません**。
主経路は HotPepper（無料）で、**HotPepper が 0 件だったときだけ** Places へフォールバックします。

この条件判定は、**純粋関数として切り出してテストで固定**しています。

```typescript
// 課金額に直結する契約なので、関数として独立させてテストする
const shouldFallbackToPlaces = ({ registeredOnly, hotpepperCount, isFirstPage }) =>
  !registeredOnly && isFirstPage && hotpepperCount === 0
```

**「低件数のときもフォールバックする」は意図的に入れませんでした。**
しきい値（3 件以下なら呼ぶ、など）は課金額を直接左右します。
実測データが無い状態で決めるべきではないと判断し、
**第一段階は「0 件のときだけ」に限定**しました。この条件なら、コストの上振れが構造的に起こりません。

### ③ キャッシュする

検索結果をキャッシュして、同じ検索で再課金しないようにしています。

キーの設計に工夫が要りました。

```
キー = 検索クエリ + 座標グリッド + 半径 + 件数
```

**座標をそのまま使うとキャッシュが効きません**（1 メートルずれただけで別キーになる）。
かといって**グリッドを固定幅にすると、狭い検索が別エリアの結果を拾います**。

そこで、**グリッド幅を検索半径から決める**ようにしました（半径の半分・上限 1km 程度）。
半径 100m の検索と半径 5km の検索で、同じ粒度を使わないためです。

もう 1 つ重要な判断があります。

> **非表示にした店舗の除外を、キャッシュに焼き込まない。**

生の検索結果を保存し、「この店は非表示」の判定は**毎回データベースを引きます**。
逆にすると、キャッシュ後に非表示化した店舗が、
**キャッシュの有効期間（現在 7 日）ずっと表示され続けます**。

### ④ 上限を設ける（fail closed）

キャッシュだけでは防げないケースがあります。
**毎回違うクエリを投げられると、キャッシュは一切ヒットしません。**

そこで、外部 API を呼ぶ直前にデータベース側で**上限を消費**します。

| 経路 | 単位 | 上限 |
| --- | --- | --- |
| エリア名の解決（未認証でも可） | IP ハッシュ + 全体 | 10/分・60/時・1,000/日 |
| 店舗検索（未認証でも可） | IP ハッシュ + 全体 | 5/分・30/時・500/日 |
| 店舗申請のプレビュー（認証必須） | ユーザー単位 | 30/時・100/日 |

> 店舗申請のフローは現在停止しています（[6.5](#65-機能を止めるという防壁)）。

設計で気をつけた点がいくつかあります。

**短窓と日次の二段にする。**
短窓だけでは総量が守れず、日次だけでは 1 人の乱用で全ユーザーが止まります。

**生の IP は保持しない。** ハッシュ化したものだけを記録し、24 時間で消します。

**消費するのはキャッシュミスのときだけ。**
守りたいのは**課金**であって、リクエスト数ではありません。
無料のキャッシュヒットまで数えると、正当な回遊が先に止まってしまいます。

**fail closed にする。** ここが重要です。

> 上限を確認できないとき（DB のエラー、想定外の戻り値）は、**外部 API を呼ばない**。

逆にすると「**守るための仕組みが壊れているときだけ無防備**」という、
最悪の壊れ方をします。

**上限到達時の振る舞いは、経路ごとに変えています。**

| 経路 | 上限到達時 |
| --- | --- |
| エリア名の解決 | **429 を返す**（代替手段が無いため） |
| 店舗検索 | **Places を呼ばず HotPepper の結果を返す**（Places は補完なので無くても成立する） |

店舗検索で 429 を返すと、「HotPepper が 0 件のときだけ検索全体が失敗する」という
**分かりにくい壊れ方**になります。黙って縮退する方が適切でした。

### ⑤ 権限を配らない

上限の判定は「台帳テーブルに何行あるか」で行います。
ということは、**行を消せる権限は、上限をリセットできる権限と同義**です。

そのため、この台帳テーブルの権限は**誰にも配っていません**。管理者権限のロールも含めてです。
上限を判定する関数自体が特別な権限で動くので、呼び出し側にテーブル権限は要りません。

### ⑥ 取得するフィールドを最小限にする

上位階層の課金は避けられませんが、**さらに上の階層**（評価・レビュー・営業時間など）は
使わないようにフィールドを固定しています。

### ⑦ サーバー側で実測する

コストを管理するには、**実際に何回呼んだか**を知る必要があります。

**GA4 では測れませんでした。** 理由は 3 つ:

| 理由 | 内容 |
| --- | --- |
| 同意ゲートで欠損 | 分析 Cookie に同意したユーザーしか計測できない |
| トラッキング防止で欠損 | ブラウザの保護機能や拡張機能がブロックする |
| PV から逆算できない | 検索画面は条件が変わるたびにリクエストが飛ぶ。**1 PV = 3〜10 リクエスト**と幅が大きい |

**サーバー側で数えれば、同意にもブロッカーにも左右されず、課金対象と 1 対 1 で対応します。**

数え方にもルールを決めました。

- **数えるのは「HTTP リクエストを出す直前」。** API キー未設定で手前で落ちる場合は
  **課金されないので数えない**
- **リクエストが出た後は成否で分けない。** タイムアウトやエラーでも
  提供元のクォータは消費されうるため、成功だけ数えると試算が過小になる
- **キャッシュヒットは別枠で数える。** ヒット率を実測できるようにするため

記録はレスポンスを返した後に非同期で行うので、**検索の応答時間に乗りません**。
記録に失敗しても検索は成功します。

この計測テーブルは**個人を特定する情報を一切持ちません**。
そして[4 章](./04-backend.md)に書いたとおり、
**「その列が存在しないこと」をテストで固定**しています。

> **運営コンソールからの呼び出しは、この防壁の外にあります。**
> admin も同じ外部 API を叩きますが、上限判定は入れていません。
> サイト全体のゲートと運営セッションの内側にあり、**未認証で到達できる web とは前提が違う**ためです。
> ただしキャッシュと allowlist の台帳は web と共有しているので、
> 同じ検索を 2 回課金することはありません。

### ⑧ 任意の ID を投げられないようにする

ここまでは店舗「検索」の話でした。**店舗詳細の取得は別経路で、別の SKU で課金されます。**

店舗詳細ページは、SEO のため**未認証で公開**しています。
つまり、URL に任意の ID を入れてアクセスできる。

素朴に実装すると、**存在しない ID を投げるだけで従量課金を無制限に発生させられます**。
キャッシュも上限も、検索経路にしか掛かっていません。

そこで、**こちらから提示したことのある ID だけを解決する**ようにしました。
検索結果として一度でも出した ID を台帳に記録しておき、
**その中に無い ID は外部 API を叩かずに 404 を返します**。

これは**最も攻撃的なコスト増幅の経路を塞ぐ**防壁で、本番で稼働中です。

> 記録するのは「Places が飲食店として返した実在店」だけなので、
> ジャンル絞り込みなどで表示から外れた店も台帳には載ります。
> 絞り込みの都合で防壁が緩むことはありません。

## 6.5 機能を止めるという防壁

防壁を積むだけでなく、**経路そのものを閉じる**判断もしました。

もともと「検索しても出てこない店を、ユーザーが申請して登録する」フローがありました。
申請時に Google マップの URL から店舗情報を解決するため、Places を呼びます。

これを**フラグで停止**しました（削除はしていません）。

理由は、**役割がほぼ無くなったから**です。

```
申請には Google マップの URL が必須
  → 「申請できる店 = Places に存在する店」
  → 検索のフォールバック（②）が同じ店を拾える
  → 申請フローの役割の大半が重複している
```

停止したことで、**この経路の課金はゼロ**になりました。

ただし、**完全に重複していたわけではありません**。
検索のフォールバックは「HotPepper が 0 件のときだけ」発火するので、
HotPepper が別の店を 1 件でも返すと、目的の店が Places にしかなくても出てきません。
申請という代替手段を閉じたことで、**この穴が唯一の取りこぼし経路**になりました。

そのため実装は消さず、**フラグを戻せば復旧できる状態**で残しています。
実測データが貯まったら、低件数でもフォールバックする案とあわせて再検討する予定です。

> **使われていない機能は、コストだけを生みます。**
> 消すのではなく止める、という選択肢を持っておくと判断が軽くなります。

## 6.6 移行を可逆にしておく

Places への移行は**段階的**に進めています。全面移行はしていません。

そのために効いたのが、**1 つ前に決めていたこと**です。

店舗の外部 ID を、店舗テーブルに直接持たせるのではなく、
**別テーブルで複数ソース分を保持する**形にしました。

```
stores（内部 ID）
   └── store_external_refs
         ├── HotPepper の ID
         └── Google の place_id
```

これにより、**両方の ID を無損失で持てます**。
ユーザーの投稿は内部 ID に紐づいているので、ソースを切り替えても無傷です。

つまり、**コストが見合わなければ即座に HotPepper へ戻せる**。

この形にした時点では、移行するかどうかも決めていませんでした。
それでも戻れる形にしたのは、**単純にコストが怖かった**からです。

個人開発なので、払えない金額になったら**その時点でサービスが終わります**。
会社なら「今期は赤字でも来期に回収する」という判断があり得ますが、
自分の財布から出す以上、上限は自分の生活費に直結しています。

だから「後から戻せない構造」を作りたくありませんでした。
外部サービスに乗るとき、**そのサービスが値上げしたら終わり**という状態は、
機能の問題ではなく**事業の継続性の問題**です。

実際、前提は変わりました（Google の課金体系変更）。
そのとき戻れないままだったら、移行するかどうかではなく
「**払えるかどうか**」の話になっていたはずです。

## 6.7 良かった点・つらい点

### 良かった点

- **試算を先にやったのが全て。** 「MAU 5,000 で $1,440」という数字を出さなければ、
  防壁を作る動機が生まれませんでした。**先に破綻することを確認する**のは重要です
- **fail closed の判断。** 「壊れているときだけ無防備」を避けられました
- **実測基盤を移行より先に作った。** 勘ではなく数字で判断できます
- **可逆性を先に確保した。** 移行するかどうか決める前に戻れる形にしておいたので、
  判断のときにコストの話だけに集中できました

### つらい点

- **防壁が多層になると、どこで止まったか分かりにくい。**
  「検索結果が少ない」とき、キャッシュなのか上限なのかフォールバック条件なのかを
  切り分けるのに時間がかかります
- **前提の失効に気づくのが遅れた。** Google の課金体系変更は 2025 年 3 月で、
  ADR を是正したのはかなり後です。**外部サービスの料金改定を追う仕組みが無い**のが課題です
- **上限値の根拠が弱い。** 5/分・30/時・500/日 という数字は、
  実測が貯まる前に決めた暫定値です。実データで見直す必要があります

## 6.8 まとめ

- 従量課金 API は**単価を下げられない。呼ぶ回数を減らすしかない**
- **先に試算して破綻を確認する。** 数字が無いと設計の動機が生まれない
- 防壁は多層で。**発火条件・キャッシュ・上限・権限・フィールド・計測・allowlist**
- **使われなくなった経路は止める。** 消さずにフラグで戻せる形にしておく
- **fail closed。** 守る仕組みが壊れているときこそ止める
- 上限到達時の振る舞いは**経路ごとに変える**。黙って縮退すべき場所もある
- **計測は課金対象と 1 対 1 で対応させる。** GA4 では代用できない
- **可逆性を先に確保しておく**と、後の移行判断が軽くなる
- そして根底にあるのは、**払えなくなったら終わりという恐怖**。
  技術的な最適化というより、サービスを続けるための条件です

---

この章の内容は、Places API に限らず**あらゆる従量課金 API に応用できます**。
LLM の API でも、決済でも、構造は同じです。

規模が大きい組織なら「まず動かして、コストは後で最適化する」が成立します。
でも**個人開発では、コストの上振れがそのまま終了条件**になる。
だから最初から怖がっておくのが、結果的にいちばん安くつきました。
