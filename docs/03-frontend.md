## 3.1 ディレクトリ設計

この設計は、以前自分が書いた記事
[モダン開発のディレクトリ構成設計！中大規模プロジェクトでも破綻しない実践的なファイル管理術](https://zenn.dev/tzp/articles/732de6448dd635)
をベースにしています。そこで整理した原則（目的の明確化・一貫性・拡張性・学習コストの最小化・
**関連ファイルの集約**）を、あじぴた向けに具体化したものです。

記事で書いた設計を実際のプロダクトで 5 ヶ月運用したことになるので、
その答え合わせも兼ねて書いておきます。

### 二層構造

```
app/                     ← Next.js App Router（ルーティング専用）
├── (auth)/              認証系
├── (onboarding)/        オンボーディング診断
├── (main)/              メインアプリ（要認証）
└── api/                 BFF（Route Handlers）

src/                     ← 実装のすべて
├── components/
├── server/              サーバー専用ロジック
├── hooks/ libs/ stores/ utils/ types/ constants/ styles/
```

**`app/` にはルーティングの定義だけを置き、実装は `src/` に集約する**方針です。
`app/[route]/page.tsx` は対応する `src/components/pages/` のコンポーネントを import するだけ。

こうしている理由は、**ルーティングの都合と UI の都合を混ぜないため**です。
App Router は `page.tsx` `layout.tsx` `loading.tsx` といった特別なファイル名の規約を持っていて、
ここに実装を書き始めると「フレームワークの規約」と「自分の設計」が同じ場所で衝突します。

### コンポーネントの 5 分類

| 置き場所 | 条件 |
| --- | --- |
| `elements/` | 最小単位の UI パーツ（Button, Input, Tag, Avatar …） |
| `layouts/` | ヘッダー・フッター・ナビ |
| `common/` | 複数ドメインで使う UI（ビジネスロジックなし） |
| `features/[domain]/` | ドメイン固有の機能（ビジネスロジックあり） |
| `pages/[route]/` | 特定ページ専用（対応する `page.tsx` からのみ import） |

判断基準は **「ビジネスロジックを持つか」「どこから使われるか」** の 2 軸だけです。

### 採用しなかった設計

| 案 | 不採用の理由 |
| --- | --- |
| **Atomic Design** | atom / molecule / organism の境界で毎回迷う。判断に時間を使う設計は続かない |
| **`index.ts` バレルファイル** | import 元が `from './Button'` になり、実体がどこか分からなくなる |
| **型・テストを別ディレクトリに集約** | 関連ファイルが散る。1 つの変更で 3 箇所を行き来することになる |

最後の点が一番効いています。あじぴたでは**関連ファイルを対象と同じディレクトリに置きます**。

```
Button/
├── Button.tsx
├── Button.test.ts
└── button.type.ts
```

コンポーネントを消すときはディレクトリごと消せる。これは地味ですが、
5 ヶ月で何度も助かりました。

### 全コンポーネントをディレクトリ形式にする

```
✅ src/components/elements/Button/Button.tsx
❌ src/components/elements/Button.tsx
```

例外なくこの形です。最初は冗長に見えましたが、
**後からサブコンポーネントや型やテストが増えたときに構造を変えなくていい**のが利点でした。
「今は 1 ファイルだから直置き、増えたらディレクトリに」を許すと、
移動のたびに import パスが変わります。

### 親専用の子コンポーネントは親の直下に置く

```
HomeStatus/
├── HomeStatus.tsx           ← 骨格のみ
├── HomeStatusAvatar/        ← 専属の子
└── HomeStatusBadge/
```

`components/` のような中間フォルダは作りません。
名前は**親名 + 役割**にして、どこに属すかを名前だけで分かるようにしています。

## 3.2 状態管理ライブラリを入れなかった

`src/stores/` にあるファイルは **2 つだけ**です。しかも zustand も Redux も使っていません。
React 標準の `useSyncExternalStore` で自作しています。

### なぜ要らなくなったのか

App Router では、**サーバー状態の置き場所が変わりました**。

```
従来（SPA）:  API を叩く → クライアントの状態管理に入れる → 画面に出す
App Router:   Server Component が直接取得 → そのまま描画
```

状態管理ライブラリの仕事の大半は「サーバーから取ってきたデータをクライアントで保持する」ことでした。
それを RSC と BFF が引き受けるなら、**残るのは本当にクライアント固有の状態だけ**です。

あじぴたで残ったのは 2 つ:

- Cookie 同意バナーの開閉と同意状態
- 通報済み口コミの一覧（表示の出し分けに使う）

この規模にライブラリは要りません。`useSyncExternalStore` で十分でした。

### 自作するときの注意点

素直に書くと**再描画ループ**が起きます。`getSnapshot` は**毎回同じ参照を返す**必要があるためです。

```typescript
// ❌ 毎回新しいオブジェクトを返すと無限ループ
const getSnapshot = () => ({ consent, hydrated, dialogOpen })

// ✅ スナップショットを変数に保持し、更新時だけ作り直す
let snapshot = INITIAL_SNAPSHOT
const setSnapshot = (next) => {
  snapshot = { ...snapshot, ...next }
  for (const listener of listeners) listener()
}
const getSnapshot = () => snapshot
```

もう 1 つは **hydration 差異**です。サーバーには Cookie 同意の状態が無いので、
初期スナップショットは常に「未 hydrate」を返し、**復元はマウント後に 1 回だけ**行います。
これをやらないと、サーバーとクライアントで描画結果が食い違います。

> **判断**: ライブラリを入れないのは「意地」ではなく、
> **この規模なら標準機能の方が壊れにくい**という判断です。
> クライアント状態が増えたら普通にライブラリを入れます。

## 3.3 パフォーマンス

ここが一番学びの多かった領域です。実測値を出しながら書きます。

### 計測の 2 系統

| 種別 | 手段 | 用途 |
| --- | --- | --- |
| **field**（実ユーザー） | Sentry | 実際のユーザーの LCP / CLS / TTFB / INP |
| **lab**（再現性重視） | 自作スクリプト | 改善の前後比較 |

**計測専用のパッケージは入れていません。** Sentry がエラー監視のために既に入っていて、
その設定で Web Vitals も自動収集されるためです。ルート単位で見られます。

lab 側は自作スクリプトで、モバイル 4G 相当にスロットリングして各ルートを複数回ロードし、
中央値を取ります。field だけだとトラフィックが少ないときに前後比較ができないので、
**同じ条件で何度も測れる手段**を別に持っています。

### 罠 1: `loading.tsx` を足したら LCP が 2 倍になった

App Router で認証必須のページは動的レンダリングになります。
Next.js 16 は**動的ルートの prefetch をスキップする**ため、
`loading.tsx` が無いとリンクをクリックしてもサーバー応答まで画面が変わりません。

そこで主要ルートに `loading.tsx` を置いてスケルトンを出すようにしました。
体感速度は上がりました。**が、初期表示の LCP が悪化しました。**

| 状態 | ホーム画面の LCP |
| --- | --- |
| `loading.tsx` 導入前 | 5.3 秒 |
| **`loading.tsx` 導入後** | **10.4 秒** ← 倍近く悪化 |
| LCP 要素に `preload` を追加 | **4.2 秒** ← 導入前より速い |

**原因**: ストリーミングされた本文は、最初は**隠し要素**としてブラウザに届きます。
すると `<Image>` が既定で付ける `loading="lazy"` が「この画像は表示領域に無い」と判定し、
**スケルトンが本文に差し替わるまで画像の取得を始めません**。

解決は、各ルートの LCP 要素（ファーストビューの画像）に `preload` を付けること。
これで取得が先に始まり、`loading.tsx` 導入前より速くなりました。

> **教訓**: `loading.tsx` を新しいルートに足すときは、
> **そのルートの LCP 要素に `preload` が付いているかを必ずセットで確認する**。
> 片方だけやると体感は良くなるのに数値は悪化します。

なお `priority` は Next.js 16 で非推奨になり `preload` に置き換わりました。内部的には同義です。
**一覧のカードのように、どれが LCP になるか画面サイズ次第で決まらない画像には付けません。**

### 罠 2: 認証チェックが毎リクエスト 1 往復していた

Next.js の proxy（旧 middleware）は**すべてのナビゲーションで、描画が始まる前に**走ります。
ここでの待ち時間はそのまま TTFB に乗り、しかも**prefetch のリクエストにも乗ります**。

最初は認証確認に「ユーザー情報を取得する」API を使っていました。
これは**毎回、認証サーバーへ問い合わせが飛びます**。

これを **JWT のローカル検証**（公開鍵を使って手元で署名を検証する方式）に変えました。
鍵は取得後モジュール内にキャッシュされるので、往復が消えます。

ただし、ここは**正確に理解しておくべき点**があります。

> 「1 リクエストあたり 1 往復」が「**0 往復**」になるのではなく、
> 「**isolate（実行環境のインスタンス）あたり 1 往復**」になる。

キャッシュは実行環境のメモリ上にあるので、コールドスタート時や別インスタンスに
振られたリクエストでは、改めて鍵の取得が発生します。

**トレードオフも受け入れています。** ローカル検証では、トークンが失効するまで（最大 1 時間）
削除・BAN されたユーザーでも proxy を通過します。

これを許容できるのは、**proxy が楽観的チェックに過ぎない**からです。
本当の権限判定はページ側の認証確認と RLS が担っています。
多層防御が前提にあるので、入口を緩めても最終的には止まります。

### 罠 3: ローカルの数値から本番を外挿できない

TTFB 改善の効果をローカルで測ると、**本番より大幅に小さく出ます**。
ローカルには DB が同じマシンにあるためです。

| 環境 | DB への 1 往復のコスト |
| --- | --- |
| ローカル | 3 〜 5 ms |
| 本番 | 約 55 ms |

**1 往復の単価が 10 倍以上違う**ので、「往復を 1 回減らす」施策の効果はローカルでは過小評価されます。
本番か field データで評価する必要があります。

### 計測時の落とし穴

認証必須ルートを測るとき、セッションが切れていると `/` にリダイレクトされます。
**この試行を中央値に混ぜてはいけません。**

以前は警告を出すだけで値は集計に入れていたため、
**ランディングページの数値がホーム画面の数値として記録されていました**。
出力の数字だけ見ても気づけません。今はリダイレクトされた試行を除外しています。

## 3.4 良かった点・つらい点

### 良かった点

- **ディレクトリ規約を先に決めたのが効いた。** 「どこに置くか」で迷う時間がほぼゼロ。
  アプリ本体だけで 3,400 コミット回せたのは、この判断コストが低かったのが大きい
- **記事に書いた設計は、実プロダクトでも破綻しなかった。** 特に
  「関連ファイルを対象と同じディレクトリに置く」は、規模が大きくなるほど効きました
- **状態管理を入れなかったのは正解だった。** 依存が 1 つ減り、
  「なぜこの状態がここにあるのか」を考える機会も減った
- **パフォーマンスを数値で見る仕組みを早めに作った。** 体感だけで判断していたら、
  `loading.tsx` の罠には気づけませんでした

### つらい点

- **ディレクトリ形式の徹底は、最初は面倒に感じる。** 1 ファイルのコンポーネントでも
  ディレクトリを切るので、手数が増えます。効果が出るのは後から
- **`loading.tsx` と `preload` の関係は、知らないと踏む。** しかも
  「体感は良くなったのに数値は悪化」なので、計測していないと気づけない
- **Next.js 16 は情報が少ない。** API が変わっている箇所があり、
  ネット上の記事が古い前提で書かれていることがあります。
  パッケージ内の公式ドキュメントを読むのが結局一番速い

## 3.5 まとめ

- `app/` はルーティング、`src/` は実装。**フレームワークの規約と自分の設計を混ぜない**
- コンポーネントは 5 分類。判断基準は「ロジックを持つか」「どこから使われるか」だけ
- **関連ファイルは同じディレクトリに置く**（型・テストを別集約しない）
- App Router ではサーバー状態を RSC が持つので、**状態管理ライブラリが要らなくなった**
- `loading.tsx` は **`preload` とセット**。片方だけだと LCP が倍悪化する
- ローカルの計測値から本番の効果を外挿しない
